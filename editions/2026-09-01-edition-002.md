## §01 Cognigy and the CCaaS field

### 2026.18 removes OAuth2 as an API authentication method, with no migration path on the page
**Cognigy · 1 Sep 2026 · BREAKING · SHIPPED · SECURITY**
Cognigy.AI 2026.18.0 shipped today. The release notes state, verbatim, that it has "Removed the OAuth2 authentication option as a supported API authentication method from the Cognigy.AI API". Two more outright removals land in the same release: the Step and Message explorers in Insights are gone, and the States tab in NLU settings along with the Set State and Reset State Nodes are gone. The Logs API moved to its own service, though endpoint routes are unchanged and no migration is required for that part.
**Why it matters:** The single highest-urgency item in the scan. Every external caller of the Cognigy.AI API needs its auth method checked before the tenant upgrades: CI/CD pipelines, custom admin tooling, Snapshot automation, external orchestrators. Anything on OAuth2 stops authenticating and there is no documented transition period. Separately, grep every customer Flow for Set State and Reset State Nodes, because those are removed rather than deprecated, and warn anyone whose Insights reporting leans on the Step or Message explorers.
*Caveat: the public release-notes index had not been regenerated to list 2026.18 at fetch time even though the version page is live. Verified directly against the version page.*
Source: https://docs.cognigy.com/release-notes/2026.18

### Blind Mode Node deprecated in favour of Data Redaction, with an April 2027 removal date
**Cognigy · 1 Sep 2026 · DEADLINE · BREAKING · SHIPPED**
2026.18 deprecates the Blind Mode Node and directs users to the Data Redaction feature instead, with removal planned for April 2027. The same April 2027 window covers deprecated LLM parameters across the AI Agent, LLM Prompt, Search Extract Output, LLM Entity Extract and Question nodes, plus the Azure OpenAI models `gpt-5-nano` and `gpt-5-mini`, whose stated migration targets are `gpt-5-4-nano` and `gpt-5-4-mini`. Using the Model field for deployment selection in Microsoft Azure OpenAI is separately deprecated with removal planned for 2027.3.0; the Deployment Name field replaces it.
**Why it matters:** Blind Mode is how a lot of older builds hide sensitive input from logs, so this is a compliance-relevant migration, not a cosmetic one. Raise it now with regulated accounts rather than in 2027, because moving from a node-level toggle to a platform Data Redaction configuration changes who owns the control and what the evidence looks like in an audit. The Azure deployment-name deprecation is the follow-through on the toggle added in 2026.17: treat the Model field as legacy in every new build from today.
*Caveat: April 2027 is published as a month with no day. 2027.3.0 is a version, not a date.*
Source: https://docs.cognigy.com/release-notes/2026.18

### DTMF barge-in and encrypted trunk transfers fixed; redaction was missing structured log payloads

## §02 Protocols and interop

### Unauthenticated RCE via attacker-supplied MCP configuration, CVSS 9.8
**gpt-researcher · 27 Aug 2026 · SECURITY**
CVE-2026-37006 carries a CVSS 3.1 base score of 9.8. A flaw in the gpt-researcher WebSocket endpoint, in v0.14.7 and earlier, lets an unauthenticated remote attacker achieve code execution by supplying malicious Model Context Protocol configurations. No GitHub Security Advisory has been published on the upstream repository as of this scan; NVD is the only source found, and it lists vendor and product as "n/a".
**Why it matters:** The generalisable lesson matters more than the specific package. MCP server configuration is an attack surface in its own right, separate from tool descriptions and tool results, and this is the first clean CVSS 9.8 demonstration of it. Audit any custom code node, webhook or admin surface that lets an end user, partner system or unauthenticated caller supply or influence MCP server configuration at runtime, and make sure MCP config is treated as privileged data that only an authenticated operator can set.
*Caveat: NVD lists vendor/product as n/a and no upstream advisory was found to cross-check the details.*
Source: https://nvd.nist.gov/vuln/detail/CVE-2026-37006

### pip install mcp now resolves to the v2 line by default, and v2 breaks from v1
**MCP Python SDK · 26 Aug 2026 · BREAKING · SHIPPED**
PyPI shows four releases landing across three lines in three days: 1.29.1 and 2.1.0 on 24 August, 2.1.1 on 25 August, 2.0.1 on 26 August. The SDK README states that `pip install mcp` now installs the v2 line by default and describes v2 as a major rework to fix long-standing architectural issues, with breaking changes from v1. The specific contents of these four patch releases could not be retrieved because GitHub API access was blocked from this environment.
**Why it matters:** Any Python tooling in your engagements that does an unpinned `pip install mcp`, or pins `mcp>=1.x` with no upper bound, can silently jump a major version on the next container rebuild. Same class of failure as the OpenAI Agents SDK default-model change in edition 001, and it lands the same way: a rebuild that changes behaviour with no code change. Pin `mcp<2` in every client repo today and schedule the migration deliberately.
*Caveat: the v2-default risk is confirmed from the SDK README, not from the contents of these four specific patch releases.*
Source: https://pypi.org/project/mcp/#history

### Unbounded SSE buffer lets a malicious server exhaust client memory
**MCP PHP SDK · 25 Aug 2026 · SECURITY · SHIPPED**
CVE-2026-53965, CVSS 4.0 score 6.9. Versions 0.5.0 through 0.7.0 of the official MCP PHP SDK's HTTP client transport append every SSE chunk to an unbounded in-memory buffer, so a malicious or compromised MCP server can stream data with no delimiter until the client exhausts memory. Fixed in 0.7.1, advisory GHSA-7m52-jw36-44r3.
**Why it matters:** Not a Cognigy dependency, but a concrete, citable instance of an MCP client trusting server-controlled stream framing. That is the right question to put to whatever MCP client library sits behind any tool-calling layer you deploy: does it bound buffer growth on a server-controlled stream, and what happens when a downstream MCP server misbehaves rather than merely goes down. Availability failure modes get much less attention than injection in MCP reviews.
Source: https://nvd.nist.gov/vuln/detail/CVE-2026-53965

### Snyk agent-scan: a free CLI that scans MCP servers and agent skill files for tool poisoning
**Snyk · 30 Aug 2026 · LAUNCH · SECURITY · COMPETITIVE**
Snyk's agent-scan is an open-source CLI that auto-discovers and scans local AI-agent components, including MCP server configurations and tool descriptions, agent skill files, and configuration across roughly a dozen agent hosts, checking for prompt injection, tool poisoning, dangerous capabilities, malicious code and credential exposure. It surfaced on Hacker News on 30 August and produces risk-scored output. Reported at 3,000-plus GitHub stars and version 0.6-plus.
**Why it matters:** Gives a concrete answer to "how do we vet a third-party MCP server before we connect it as a Cognigy tool", which is currently answered with manual review or nothing. Proposing a scanner as a pre-integration gate is a cheap, defensible control to put in a client architecture review, and it targets exactly the tool-poisoning class the Context7 CVE in edition 001 demonstrated. Try it against an MCP server you already trust before recommending it, so you know its false-positive rate.
*Caveat: version, star count and date come from the repo description and an HN submission timestamp, not a formal release announcement. Scan coverage and accuracy not independently verified. Vendor-produced tool from a security vendor.*
Source: https://github.com/snyk/agent-scan

### MCP roadmap adds an Agent Identity working group and previews a tools/call result-shape redesign
**Model Context Protocol · 22 Aug 2026 · PROPOSED, not shipped · RESEARCH**
The roadmap updated 22 August names five priority areas beyond the 2026-07-28 spec: composing Tasks, `subscriptions/listen` and progress into one lifecycle with server-initiated push and webhooks; HTTP-native transport unification, including running Streamable HTTP over stdio via HTTP/2 for local servers plus ETag caching on top of `ttlMs` and `cacheScope`; a forming Agent Identity working group targeting Workload Identity Federation (SEP-1933), ID-JAG and RFC 8693 token exchange alongside DPoP; a redesign of the `tools/call` result shape to resolve the `content` versus `structuredContent` ambiguity; and an extension contract defining host, client, server and agent extension roles.
**Why it matters:** The identity workstream is the eventual standard answer to "how does a sub-agent get scoped credentials instead of sharing one API key", a live question in every multi-agent design review. Say plainly that it is roadmap, not real, when a client pushes for it now, and design a mapping layer you can swap. The `tools/call` result-shape redesign is the forward-looking breaking change: anything you write today that parses MCP tool results should isolate that parsing behind one function.
*Caveat: everything here is proposed or in progress. Both the Agent Identity and Core Primitives working groups are still described as forming.*
Sources: https://modelcontextprotocol.io/development/roadmap · https://blog.modelcontextprotocol.io/posts/mcp-roadmap/

### WebMCP is a Community Group draft, not a W3C standard, and now carries a prompt-injection threat model
**W3C WebML CG · 26 Aug 2026 · CORRECTION · RESEARCH · COMPETITIVE**
WebMCP, which lets a web page expose JavaScript tools directly to an AI agent, published an updated Draft Community Group Report on 26 August. It is a CG draft, not a W3C Recommendation. The draft has an explicit security and privacy section covering prompt injection, intent misrepresentation and privacy leakage from page-exposed tools, and open issues remain on tool activation and cancellation events and on cross-document execution.
**Why it matters:** Closes an open question from edition 001, which could not confirm the claim that WebMCP is an official W3C standard. It is not, and now there is a primary source to say so if a client or integrator quotes it as settled. Watch it anyway: page-declared tools are a genuinely different exposure surface from a hosted MCP server, and every piece of untrusted-input scrutiny applied to third-party MCP tool descriptions applies to these too.
*Caveat: pre-standard CG draft. Not previously tracked in this series, so treat as new background rather than a delta.*
Source: https://webmachinelearning.github.io/webmcp/

## §03 Voice and speech models

### Telephony codec question answered: Flux and Sonic-3.6 do 8 kHz mu-law and A-law, Gemini does not document it
**Deepgram / Cartesia / Google · 1 Sep 2026 · CORRECTION · RESEARCH**
Edition 001 flagged 8 kHz mu-law and A-law output as unconfirmed across every new TTS model. Deepgram's TTS encoding reference confirms Flux streaming supports `linear16`, `mulaw` and `alaw`, with mulaw and alaw restricted to 8000 or 16000 Hz, raw and uncontainerized only; compressed formats such as mp3 and opus are batch REST only. Cartesia's TTS API reference confirms `pcm_mulaw` and `pcm_alaw` at 8000 Hz across models including Sonic-3.6. Google's Gemini speech-generation and Live API reference pages document no encoding or sample-rate parameter at all, mentioning only 24 kHz 16-bit PCM output.
**Why it matters:** Settles the highest-value follow-up from the last scan. Flux and Sonic-3.6 can sit directly on an 8 kHz mu-law or A-law trunk with no transcoding hop, which removes both a latency cost and a CPU cost from the Voice Gateway audio path, and it is now a confirmable statement to make in a design review. Gemini's speech stack looks like it needs a 24 kHz to 8 kHz resample and transcode stage, so do not put it in a telephony-facing architecture diagram until the output format has been tested directly.
*Caveat: read Gemini as not confirmed as supported in the reachable documentation, not as confirmed absent. The speechConfig schema could not be fully expanded via fetch.*
Sources: https://developers.deepgram.com/docs/tts-encoding · https://docs.cartesia.ai/api-reference/tts/tts · https://ai.google.dev/gemini-api/docs/speech-generation

## §04 Frameworks, eval and observability

### Pydantic AI durable-execution surface ships and then breaks twice inside four days
**Pydantic AI · 1 Sep 2026 · BREAKING · SHIPPED**
v2.36.0 on 29 August introduced a public `@durable_operation` decorator with a documented backend API intended for third-party durable-execution engines, making explicit operation names a required argument and breaking anyone relying on inference. v2.37.0, released today, extended the same surface by rejecting per-run capability parameters on DBOS-backed systems to match Temporal's behaviour, also flagged as breaking.
**Why it matters:** Direct evidence that durable-execution-for-agents is still churning upstream rather than stabilising, which is useful to say out loud in an architecture review. If any client design pairs Cognigy with a Pydantic AI orchestrator behind Temporal or DBOS, pin the exact patch version and re-test on any bump past 2.35.x. It is also a clean contrast: Cognigy's flow engine already owns durable conversational state natively, against a bolt-on layer that broke twice in one week.
*Caveat: release-note content summarized from GitHub release pages rather than read verbatim. The breaking-change fact is confirmed across two independent release pages.*
Source: https://pypi.org/project/pydantic-ai/#history

## §07 Method and known limits

- The nominal window is a single day, 1 September, because edition 001 closed on 31 August. Each vendor lane also swept back to roughly 20-25 August and reports only what edition 001 did not carry. Catch-up items are dated as published, so the card dates are honest even where they precede the stated window.
- Both discovery lanes were skipped. This is stated on the page, in this archive and in the source-health panel rather than being left as silence.
